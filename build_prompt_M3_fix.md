## The problem: `realpty.Close()` doesn't use process groups, only kills the direct child PID

In `realpty.go`, `Close()` sends `SIGTERM`/`SIGKILL` directly to `t.pid` (the shell's own PID) — it never puts the shell in its own process group and never signals a group. You noted in your report: "En este entorno, `Setpgid` hacía fallar el arranque PTY con `operation not permitted`, así que el cierre quedó con SIGTERM/SIGKILL al PID directo."

This matters beyond just M3: the design doc (`~/tesla/DASHBOARD_TERMINAL_DESIGN.md`, round 10) already decided the crash/orphan-cleanup mechanism (a future milestone, M5) is built on **process groups** — each PTY child starts in its own process group, and stale-session reconciliation on next backend startup finds and kills lingering process groups. If M3 abandons process groups now, M5 has no foundation to build on, and there's a more immediate problem too: if the shell spawns child processes (a background build, a long-running command), closing the session today only kills the shell itself — any children become orphaned and keep running silently, un-noticed, with no cleanup at all. That's a real correctness gap for the "close a session" action, not just future crash recovery.
