The user wants to be able to "program from a web dashboard as if it were Claude CLI or Claude Desktop" — type a request in a browser, have an AI agent actually read/edit files and run commands on the user's own Mac, with the human able to watch and take over control of a real terminal at any point.

## What already exists — four repos, four different roles

1. **`~/tesla`** — a design document, `DASHBOARD_TERMINAL_DESIGN.md`, produced over **10 rounds of iterative critique** between a Claude session and Codex (Claude proposes a design, Codex critiques it hard, repeat until sound). It covers: WebSocket auth model, an actor-goroutine-per-PTY-session ownership model (agent vs. human, epoch-based, race-free), `launchd` socket-activation daemon lifecycle (Shape A — no separate supervisor), crash recovery via process groups, and the productization decisions (session model, terminal UI semantics). This is **closed** — read it for the "why" behind everything in `exo`, don't reopen these decisions without a real reason.

2. **`~/exo`** — a **new, working Go implementation** of everything in that design doc, built module-by-module (M0 through M7) using a specific workflow: a Claude session writes a detailed build prompt per milestone → Codex actually writes the code and tests → Claude reviews the real code (not just Codex's report), runs `go build`/`go vet`/`go test -race` itself, and for UI milestones does real manual browser verification (clicking, typing, checking network responses) before signing off. Read `~/exo/IMPLEMENTATION_PLAN.md` — it has the full milestone history including several real bugs Claude's review caught that Codex's own tests missed (a CORS/Origin bug that broke session listing entirely, a CSS bug that made the "take control" UI silently non-functional, and a WebSocket frame-type bug that meant **no keystroke had ever reached a real shell** through the UI until it was found and fixed). This is the pattern you must continue for M8 — do not skip the "Claude reviews Codex's actual code and does real end-to-end verification" step, it caught real product-breaking bugs every single time it was done.

   `exo` currently implements: a real PTY-backed terminal (`realpty`), the ownership/epoch session actor (`ptyactor`), the browser transport with auth/CORS/CSRF (`termserver`), multi-session support (`sessions`), the `launchd` daemon lifecycle (`backend`, `launchdsocket`, `singleton`, `lifecycle`, `launchagent`, `cli`), crash/orphan recovery (`sessionstore`), and a real xterm.js browser UI (`termserver/assets`). It has **zero AI in it** — today it is exactly a secure, remotely-controllable terminal with nobody driving it but a human. `exo` module: `github.com/DiegoAvila-yeyo/exo`, depends on `github.com/yeyoos/nucleo-base` via a local `replace` in `go.mod` (they're sibling directories under `~`).

3. **`~/nucleo-base`** — a 5-layer "clean architecture" Go monorepo (`layer1-harness-shell` through `layer5-learning-evidence-guardrails`, plus `shared/`) that is mid-port from `~/pacta-harness/standalone/internal`. Read `~/nucleo-base/ARCHITECTURE_MAP.md` for the full dependency graph and layer classification of every package. Critically: **the AI agent already exists here** — `layer2-runtime-rails/agent` (the agent turn loop), `layer2-runtime-rails/runtime` (the coordinator), `layer2-runtime-rails/provider` (actual LLM API calls), `layer2-runtime-rails/tool` (the tool registry — `bash`, `edit`, `writefile`, `terminal_open/write/read/list/kill`, and many more), `layer2-runtime-rails/instructions`, `subagent`, `skills`, `workflow`. There is also an existing (older, less capable) web dashboard at `layer1-harness-shell/dashboard` (`chat.go`, `server.go`, `broadcaster.go`) that already runs this same agent from a `POST /api/chat` HTTP endpoint with SSE streaming and a human-approval flow — but its own terminal handling (`layer2-runtime-rails/terminal`) is markedly weaker than what was built in `exo`: no resize support, cursor-based file-polling reads instead of a real actor/subscribe model, no ownership arbitration between agent and human. `nucleo-base` has no runnable `main.go`/binary yet — it's a library-shaped mid-port, verified to `go build ./...` cleanly as of this session.

## What M8 actually is

Connect the AI agent that already exists in `nucleo-base` to the terminal infrastructure that already exists in `exo`, so that a chat message typed in the browser causes the *agent* to drive the real, secure, ownership-aware terminal `exo` built — not a human typing directly. The end state: open the dashboard, type "fix this bug," watch the agent actually work in a live terminal you can see and take over at any point, using everything already built in rounds 1-10 (design) and M0-M7 (implementation).
